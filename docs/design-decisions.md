# Ontwerpkeuzes

De oorspronkelijke opdracht vroeg Supabase: Edge Functions voor de spelregels, Postgres voor de opslag en anonieme Auth voor identiteit. Die opdracht staat niet meer in de repository; de Nederlandse documentatie onder `docs/` is leidend. De spelregels staan in één TypeScript-pakket zodat unit tests en de server dezelfde reducer gebruiken, en een Edge Function importeert dat pakket niet betrouwbaar. Daarom is `services/game-api` de autoritatieve server: één Node-proces dat draait waar een container draait. Supabase is niet in gebruik. De opslag is gewone Postgres via `DATABASE_URL` en de identiteit komt van de API zelf.

Elke browser krijgt een eigen, door de API ondertekend token (dev-login). Dat is een tijdelijke, anonieme identiteit per browser, geen account. Er is bewust geen externe identiteitsdienst: het spel vraagt geen persoonsgegevens en een rol hoort bij één browser voor de duur van een sessie. Online moet dev-login expliciet aan staan (`ALLOW_DEV_AUTH=true`) met een eigen `AUTH_SECRET`.

Sessies leven altijd in het geheugen. Een kopie is optioneel: lokaal een JSON-bestand (`GAME_FILE`), of Postgres via `DATABASE_URL`. Op Azure staat Postgres standaard uit (`enablePostgres=false`): goedkoper, maar een herstart of deploy wist alle sessies. Zet hem aan als je dat wilt vermijden. Schrijven naar Postgres gebeurt niet na elke tick of heartbeat: wijzigingen worden gebundeld (`PERSIST_INTERVAL_MS`, standaard 15 s). Nieuwe en gesloten sessies gaan meteen weg. Verlaten sessies (geen commando/heartbeat gedurende `SESSION_IDLE_MS`, standaard 30 minuten) en verlopen sessies worden gesloten en uit geheugen én (indien aanwezig) Postgres verwijderd. Nieuw aanmaken is begrensd op `MAX_OPEN_SESSIONS_PER_IP` open sessies per client-IP (standaard 10), zodat één netwerk niet eindeloos lobbies kan openen. Die limiet beschermt de gehoste API en geldt standaard alleen met `NODE_ENV=production`. Lokaal komen alle verzoeken via de Vite-proxy van hetzelfde adres, zodat testtafels en herstarts de limiet anders snel vullen.

Hosting: één Docker-image op Azure Container Apps, uitgerold door GitHub Actions bij elke push naar `main`. De API is één langlopend proces: sessies in het geheugen, een tik elke 500 ms en open SSE-verbindingen. Dat vraagt één vaste instantie, geen kortlevende functies; de Container App staat daarom vast op één replica. Met een paar spellen van vijf deelnemers tegelijk is dat ruim genoeg; hoge beschikbaarheid is geen doel. De code hangt niet aan Azure: de image draait op elk platform dat één container biedt (en optioneel Postgres). Zie [deployment.md](deployment.md).

De image bevat nginx en de API samen. nginx serveert de website en stuurt `/api` door, zodat browser en API één adres delen. Dat scheelt een aparte website-hosting, CORS-instellingen en een API-adres dat in de build moet worden gebakken, en lokaal draait met `docker compose` exact dezelfde image als online. De prijs is twee processen in één container; een klein startscript stopt de container zodra een van beide wegvalt. De API start in de container met `tsx`, net als lokaal en zonder aparte build, omdat het domeinpakket als TypeScript-bron wordt geïmporteerd.

De pipeline logt bij Azure in met OIDC, zodat er geen Azure-wachtwoord in GitHub staat. Hij krijgt de rol Contributor op de resources van de game: de Container App, de omgeving, de registry en de pull-identity. Smallere rollen per resource zouden hem evengoed de Container App laten beheren, inclusief de geheimen die daarop staan, dus de winst daarvan is klein. Door de rol niet op de hele resource group te zetten, kan de game ook in een gedeelde resource group staan zonder dat de pipeline bij andere resources kan. De database is bereikbaar voor verbindingen die binnen Azure ontstaan, met TLS en een wachtwoord. Een virtueel netwerk is strenger, maar kost meer en maakt de installatie zwaarder dan dit spel nodig heeft.

De file staat op dag 2, 04:30, vóór 05:00, 06:00 en 08:00. Hoeveelheid is 1. De presentatie duurt 3000 ms en de BDI-pipeline 1000 ms, beide via omgevingsvariabelen.

`SUBSCRIPTIONS` bestaat alleen met BDI. Vergelijking ontstaat alleen als ronde 1 en ronde 2 allebei zijn gespeeld.

Ideeën die destijds in die opdracht als backlog stonden (zoals een tweede Association) zijn niet gebouwd. Nieuwe pack-voorstellen staan in [games/voorstellen.md](games/voorstellen.md).

Pack `access` (*Wie mag deze gegevens zien?*) heeft een eigen reducer en `session.access`-document in plaats van de logistieke stappen S00–S20 en de zonder/met-BDI-rondes. Die game past niet in de meerkeuze-en-outbox-flow; sessie, QR-rollen, pauze, tick en persist blijven gedeeld.

In `access` neemt de speler van de Data Service Provider het toegangsbesluit zelf: per verzoek raadpleegt hij het Association Register, het Orchestration Register en het beleid van de Data Owner, en kiest leveren of weigeren. De server bepaalt de waarheid per laag en keurt het besluit goed of af (geen levering zonder alle bronnen, geen levering bij een "nee", geen weigering zonder reden). Zo ervaren spelers dat het besluit lokaal valt op bewijs uit onafhankelijke bronnen. In werkelijkheid doet de BDI Connector dit automatisch; dat komt terug in de begrippen en de nabespreking.

Authenticatie is in `access` geen losse stap maar onderdeel van elk verzoek: Delta ondertekent het token met de eigen private key (zoals in het trust-anchor-model) en LogiData controleert het met de sleutel uit het Association Register. Het token van gisteren laat zien dat authenticatie per verzoek faalt terwijl het lidmaatschap blijft. De token-claims op de beamer zijn illustratief; de BDI schrijft geen claimprofiel voor.

Voorspellingen in `access` hebben geen `expectedVersion`, verhogen de versie niet en mogen tijdens de presentatiepauze. Vier spelers voorspellen tegelijk; met versiecontrole zouden ze elkaar en LogiData steeds een conflict geven. Ze sluiten zodra LogiData de eerste bron raadpleegt of besluit, en uiterlijk 15 seconden na de presentatiepauze (pauzeren schuift die termijn mee).

Foute keuzes in `access` blijven in de scène staan, met uitleg op beamer en telefoon; de speler kiest opnieuw. Ze tellen als leermoment in de nabespreking, niet als strafpunt.
